# 이벤트 스크립트 VM — 오퍼코드 표와 텍스트 경계 (2026-08-16 확정)

이 문서가 **이벤트 대사(452 KiB)의 정본**이다. `docs/07` 의 이벤트 절은
"구조 미확정" 상태로 멈춰 있었고, 그 병목이 여기서 풀렸다.

## 0. 한 줄

**텍스트의 시작과 끝을 기계로 판정할 수 있다.**
오퍼코드 `0x01` 바로 뒤에서 시작해 `0x00` 에서 끝난다. 도구는
`scripts/evscript.py`(워커) + `scripts/evsim.py`(핸들러 추상 실행기)다.

```bash
python scripts/evscript.py reach "roms/Star Ocean - Blue Sphere (Japan).gbc"
python scripts/evscript.py text  "roms/Star Ocean - Blue Sphere (Japan).gbc"   # -> out/evtext.tsv
```

| 실측 | 값 |
|---|---|
| 진입점 | 1,548 (표 `0x224000`, 3 B `[뱅크][lo][hi]`) |
| 방문 오퍼코드 | 63,700 |
| **텍스트 런** | **5,470 개 / 182,428 B** |
| 점프표(데이터) | 58,890 B |
| 커버 | 455,576 B — 실제 스크립트 범위(`0x225225~0x29B009`)의 **약 95%** |
| 측정 실패 | 98 (0.15%) |

⚠ **뱅크 166 도 스크립트다.** `docs/07` 의 옛 기록(137~165)은 틀렸다.
실측 커버 범위는 뱅크 **137~166**. 뱅크 168 은 스크립트가 아니라 코드다
(`call $40B9` 사이트가 `0x2A0019` 이후에 8곳 있다) — 그래서 상한을 `0x2A0000` 으로 잡는다.

## 1. VM 본체 — 뱅크 14 `$412E`

```
412E  cd b9 40   call $40B9      ; 스크립트에서 1바이트 = 오퍼코드
4131  47         ld b,a
4132  21 48 41   ld hl,$4148     ; ← 점프 테이블
4135  87         add a, a        ; A*2 (carry -> inc h)
4136  30 01      jr nc,$4139
4138  24         inc h
4139  85         add a, l
413A  6f         ld l,a
413B  30 01      jr nc,$413E
413D  24         inc h
413E  2a         ld a,(hl+)
413F  66         ld h,(hl)
4140  6f         ld l,a          ; HL = 핸들러
4141  78         ld a,b          ; ⛔ **오퍼코드를 A 로 넘긴다**
4142  cd 47 41   call $4147      ; -> jp hl
4145  18 e7      jr $412E        ; 무한 루프
4147  e9         jp hl
```

### 점프 테이블 `$4148` — **133 엔트리** (오퍼코드 `0x00`~`0x84`)

크기 자기증명 두 겹:

- 0x85 번째 값이 `$F1C9` 로 **뱅크 밖**이다(핸들러일 수 없다).
- 표 끝이 `$4251` 이고, `$4253` 은 `$4114 ld hl,$4253` 이 쓰는 **이미 아는 타일
  데이터**다. 즉 표 뒤에 다른 것이 붙어 있다.

## 2. ⛔ 텍스트 — 오퍼코드 `0x01`

```
436C  cd 7c 02   call $027C
436F  cd de 40   call $40DE    ; 글자 1개 (리드바이트면 2바이트를 먹는다)
4372  b7         or a
4373  c8         ret z         ; ← 0x00 = 문자열 끝, VM 루프로 복귀
4374  fe 10      cp $10
4376  38 05      jr c,$437D    ; 0x01~0x0F = 텍스트 **내부** 제어
4378  cd 9e 48   call $489E    ; 0x10~0xFF = 글리프 렌더
437B  18 ef      jr $436C
```

⇒ `01 <글자들…> 00`. **NUL 종단이고 길이 접두가 없다.**
리드바이트(`0x5E`/`0x5F`, 확장 후 `0x5C~0x5F`)는 2바이트를 먹으므로
**둘째 바이트가 `0x00` 이어도 종단이 아니다** — `docs/07` 의 그 함정 그대로다.

### 텍스트 내부 제어 — 표 `$438F`, 16엔트리

| 코드 | 핸들러 | 뜻 | 피연산자 |
|---|---|---|---|
| `{00}` | — | **문자열 끝** | — |
| `{01}` | `$43F1` | **줄바꿈** | 0 |
| `{02}` | `$4413` | 상자 그리기 | 0 |
| `{03}` | `$43B0` | **쪽 넘김**(`$443F` + `$4413`) | 0 |
| `{04}` | `$44CF` | 수치 출력 | 1 |
| `{05}` | `$4531` | 이름 출력 | 1 |
| `{06}`,`{0A}`~`{0F}` | `$43AF` | `ret` (no-op) | 0 |
| `{07}` | `$4554` | `ret` (no-op) | 0 |
| `{08}` | `$4555` | 창 파라미터 | 1 |
| `{09}` | `$43B0` | `{03}` 과 같다 | 0 |

디코드 예 (실측, `0x295319`):

    いったい　{K:151}が{01}{K:19A}きたいのさ？{03}こんな　トコロくらい{01}{K:17C}{K:183}の{K:113}

`{01}` 이 줄바꿈, `{03}` 이 쪽 넘김 자리에 정확히 들어간다. **5,470 런이 전부
이렇게 깨끗한 일본어로 떨어진다** — 경계 판정이 맞다는 가장 강한 증거다.

## 3. ⛔ 피연산자는 **선택자로 형이 정해진다** — 고정 길이표는 틀린다

여기서 한 번 크게 틀렸다. 기록해 둔다.

```
4263  cd b9 40   call $40B9        ; 선택자 1바이트
4266  cd 05 30   call $3005        ; ROM0 "인라인 점프표" 헬퍼
4269  71 42 78 42 81 42 88 42      ; ⛔ 코드가 아니라 **데이터**(4엔트리)
4271  call $40B9 / ld e,a / ld d,$00 / ret            ; sel 0 = 8비트 즉치  (+1)
4278  call $40B9 / ld e,a / call $40B9 / ld d,a / ret ; sel 1 = 16비트 즉치 (+2)
4281  call $40B9 / call $42E9 / …                     ; sel 2 = 변수 참조   (+1)
4288  call $4278 / call $4309 / …                     ; sel 3 = 간접 16비트 (+2)
```

`$3005` 는 `pop hl` 로 **복귀주소를 표의 시작으로 삼는** 고전적 트릭이다.

```
3005  e1 pop hl / 87 add a,a / 85 add a,l / 6f ld l,a / (nc? inc h)
300C  2a ld a,(hl+) / 66 ld h,(hl) / 6f ld l,a / e9 jp hl
```

⇒ 같은 오퍼코드라도 **선택자에 따라 길이가 다르다.**
CFG 로 `call $40B9` 횟수만 세면 `call $3005` **다음의 표 바이트를 코드로 흘려 읽어**
첫 엔트리($4271)로 들어가 "항상 2바이트"라는 **그럴듯하고 틀린 답**이 나온다.
빌드도 검증도 안 하는 단계라 조용히 넘어갈 뻔했고, **선형 훑기가 33% 에서
막혀서** 잡혔다.

같은 꼴의 두 번째 디스패처가 `$4292` 에 또 있다(표 `$4298`, 4엔트리, `$42A0` 이
첫 핸들러라 크기 자기증명).

### 그래서 — 정적 길이표를 버리고 **추상 실행**으로 잰다

`scripts/evsim.py` 가 핸들러를 **실제 스크립트 바이트를 물려 가며** 실행한다.
레지스터·플래그는 아는 만큼만 값으로 들고(모르면 `None`), 분기 조건을 모르면
양쪽을 다 간다. 스크립트에서 읽은 값은 전부 구체값이라 **선택자 분기는 항상
결정된다.**

## 4. 제어 흐름 — 선형 훑기가 안 되는 이유

| 오퍼코드 | 핸들러 | 하는 일 |
|---|---|---|
| `0x00` | `$4367` | `call $4A37 / pop af / ret` — **VM 루프의 복귀주소를 버린다 = 종료** |
| `0x01` | `$436C` | 텍스트 |
| `0x04` | `$4C46` | **상대 점프** — 2바이트 변위를 읽어 `$4084` 로 이동 |
| `0x05` | `$4C52` | **switch** — 아래 |
| `0x06`~`0x09` | `$4C5E` | 비교 후 점프(`$4C46`) 또는 2바이트 건너뛰기 |
| `0x0A`,`0x0F` | `$4CAE`,`$4CAA` | 예/아니오 — `[2B][2B]` 슬롯 2개, 취소면 4바이트 통과 |
| `0x45` | `$5421` | **2단 오퍼코드** — 서브 표 `$5435`, 11엔트리 |
| `0x49` | `$56FF` | 라벨 등록 + `0x00` 종단 바이트열 |
| `0x5B` | `$5F66` | `ld b,$08` 루프 → **9바이트 고정** |
| `0x5D` | `$5F85` | `0x00` 종단 바이트열 |

### `$4084` = 스크립트 포인터 += HL — **두 얼굴이다**

- HL 이 **상수**면 (`ld hl,$0005` → `call $4084`) = 피연산자 N바이트 건너뛰기
- HL 이 **계산값**이면 (스크립트에서 읽은 값) = **점프**

구분하지 않으면 길이표가 조용히 틀린다.

### 오퍼코드 `0x05` = switch — 표 크기가 **자기증명**된다

```
05 <피연산자>  [2B 변위 × N]
```

`$4C52` 는 `pos += 2*값` 한 뒤 그 자리에서 2바이트를 읽어 또 점프한다.
**N 은 스크립트 어디에도 없다.** 대신 표가 끝나는 곳이 곧 **가장 낮은 목적지**다
(이 프로젝트의 다른 풀들과 같은 자기증명). k 를 늘리다가 표 끝이 최소 목적지에
닿으면 거기가 끝이다. 실측 표 하나가 18엔트리였고 첫 목적지와 정확히 맞았다.

⇒ **선형으로 훑으면 이 표를 오퍼코드로 오해한다.** 그래서 워커는
   **진입점에서 제어 흐름을 따라간다.** 표는 아무도 밟지 않으므로 자동으로 걸러진다.

## 5. 스크립트는 **뱅크를 넘어 이어진다**

```
$40B9  inc hl / bit 7,h / (넘었으면) 뱅크+1, HL=$4001
$4084  HL += disp;  HL >= $8000 인 동안 HL += $C001(= -$3FFF), 뱅크+1
```

한 뱅크가 스크립트에 내주는 것은 `$4001~$7FFF` 의 **0x3FFF 바이트**이고
**각 뱅크 첫 바이트(뱅크 ID 각인)는 건너뛴다**(`docs/06` 의 뱅크 규약).
파일 오프셋을 그냥 `+1` 하면 뱅크마다 한 바이트씩 어긋난다 —
`evsim.Sim.adv()` 가 이걸 처리한다.

## 6. 추상 실행기에서 실제로 밟은 함정 네 개

전부 "그럴듯한 답이 나오는데 틀린" 부류다.

1. **오퍼코드를 A 로 안 넘기면** `0x06`~`0x09` 가 통째로 측정불가가 된다.
   핸들러가 `push af / … / pop af / sub $06 / and $03 / call $3005` 로
   **A(=오퍼코드)를 보고 갈라지기** 때문이다.
2. **값 스택 없이 `pop af` 를 `None` 으로 뭉개면** 위의 A 복원이 죽는다.
3. **상태 키에 콜스택 *깊이*만 넣으면 안 된다.** ROM0 호출 뒤 레지스터가 전부
   `None` 이라 서로 다른 호출지점의 상태가 같아 보이고, 먼저 처리된 쪽만 남아
   **복귀가 통째로 사라진다**(`$4D7F` 를 부르는 4곳 중 한 곳으로만 돌아갔다).
   → 키에 **콜스택 전체**를 넣는다.
4. **ROM0 로의 무조건 점프는 꼬리호출이다.** "뱅크 밖"이라고 포기하면
   `jp $0519` 하나 때문에 `0x03`·`0x6B`~`0x6E` 가 전부 측정불가가 된다.
   ROM0 루틴은 스크립트 포인터를 안 건드리므로 "불투명 호출 + ret" 로 본다.

### ⛔ 5번째 — 구제 런의 **시작이 몇 바이트 이르다** (2026-08-16)

구제 패스(`evexport.salvage`)는 워크가 못 닿은 영역을 `0x01 … 0x00` 으로 훑는다.
그런데 **점프표·데이터의 바이트가 우연히 `0x01`** 이면 진짜 텍스트 오퍼코드보다
앞에서 런이 시작된다. 그대로 두면 `evrepack` 이 스텁을 그 자리에 써서
**진짜 오퍼코드를 지운다** — 빌드도 되읽기 검증도 통과하고 실기에서만 깨진다.

실례: 카지노 장면 `0x235078`. 앞의 점프표가 `1B 00 46 00 6D 00 92 00 BE 00
E3 00 08 01` 인데 마지막 항목 `08 01` 의 **윗바이트 `01` 을 텍스트 오퍼코드로**
읽어, 뒤따르는 코드 `77 71 6B` 를 대사 「ぜすぎ」로 붙였다. 진짜 대사는
`0x23507D` 의 「はっずれ〜」다.

판정 근거(자기증명): 같은 세 바이트 `77 71 6B` 가 스크립트 영역에서 **워크가
제어 흐름으로 확정한 텍스트 오퍼코드 바로 앞에 12번** 나온다. 대사라면 그럴
수 없다 — 코드다. 그래서 `reanchor()` 가 「런 안의 `01` 앞 바이트열 `P` 에 대해
`P 01` 이 **워크 확정 오퍼코드 앞**에 2번 이상 나오면 `P` 는 코드다」로 시작을
옮긴다. 워크 결과만 근거로 쓰므로 구제분끼리 서로를 정당화하지 않는다.

⇒ 전수 6줄이 잡혔다(`0x235079` `0x235092` `0x2350BD` `0x2350E8` `0x257CF0`
`0x2949F6`). 나머지 313줄은 그대로 — 마스터 줄 수·번역 1,254줄 불변.

**2차 (같은 날, 배치 21 작업 중)** — 앞머리 **전체만** 보면 놓친다.
몬스터 사진상 `0x2436D8` 은 `04 8C 07 03 2F 01 5B…` 로 시작하는데, 앞머리
전체 `04 8C 07 03 2F` 는 피연산자 `8C` 가 매번 달라 ROM 에 한 번뿐이라
안 걸렸다. **끝 2바이트**(`03 2F`)로 보면 `03 2F 01` 이 31번 나오고 그중
**8번이 워크 확정 오퍼코드 앞**이다 — 코드가 확실하다.
⇒ `reanchor` 가 앞머리 전체와 **끝 2~4바이트**를 함께 본다(1바이트는 흔해서
오탐이 난다). 추가로 **20줄**이 잡혔다(사진상 15 + `0x260B8A` `0x271854`
`0x294D1A` `0x2989F9` `0x29906B`). 번역이 들어 있던 줄은 0개.

교훈: **구제 런은 「그럴듯한 일본어가 나온다」로 검증되지 않는다.** 앞에
붙은 코드가 우연히 글자로 읽히기 때문이다. 판정은 항상 **워크가 제어 흐름으로
확정한 것**에만 기대야 한다.

그리고 **손으로 디스어셈블할 때 오프셋을 틀리지 말 것** — 뱅크 14 는
`파일 0x38000 + (cpu - 0x4000)` 이다. `0x39000 + …` 로 잘못 잡아 `$50xx` 를
`$60xx` 라 부르며 "핸들러가 명령 중간을 가리킨다"고 한참 헤맸다.

## 7. 남은 것

### 측정 실패 98건 (0.15%)

| 사유 | 수 | 메모 |
|---|---|---|
| `0x11`,`0x12` 측정불가 | 35 | `$4292` 선택자가 4 이상으로 읽힌다 = 이미 어긋난 자리일 가능성 |
| `0x4A` 측정불가 | 23 | 스텝 초과 — 메뉴/선택지 오퍼코드, 루프가 크다 |
| 미정의 오퍼코드 | 나머지 | 대개 죽은 코드이거나 위 실패의 하류 |

미커버 27,185 B(5.7%)도 같은 하류일 가능성이 크다.
**번역 자체를 막지는 않는다** — 텍스트 런은 겹치지 않고(겹침 1건),
점프표와도 사실상 분리돼 있다(교집합 2 B).

### ⛔ 다음 단계는 **재패킹 설계**다 (아직 하지 말 것)

텍스트가 스크립트 안에 인라인이고 **점프가 전부 2바이트 상대 변위**라,
텍스트 길이가 바뀌면 그 텍스트를 넘어가는 모든 변위가 깨진다.

지금은 **모든 점프 사이트와 목적지를 안다**(워커가 제어 흐름을 다 따라간다).
그러니 어셈블러의 릴랙세이션과 같은 방식이 가능하다:

1. 바이트마다 역할을 붙인다(코드 / 텍스트 / 점프표) — 워커가 이미 낸다
2. 텍스트를 한국어로 바꾸고
3. 모든 변위를 새 배치에 맞춰 **다시 계산**한다(변위는 2바이트 고정이라
   길이가 변하지 않으므로 한 번에 수렴한다)
4. 포인터 표 `0x224000` 의 1,548 엔트리를 갱신한다

⚠ 선행 확인 두 가지:
- **바깥에서 스크립트 주소를 직접 참조하는 코드가 있는가.**
  `docs/07` 의 "표는 옮기면 안 된다" 교훈이 여기에도 적용된다.
- **글리프 2단계 확장**(`docs/06`, page5~7 → 2048). 빈 슬롯 178개로는
  182 KB 대사를 감당하지 못한다.

대안으로 "새 오퍼코드 `0x85` = 원거리 포인터로 문자열 출력"을 추가하고
인라인 텍스트를 3바이트 스텁으로 바꾸는 길도 있다(점프 변위가 안 흔들린다).
점프 테이블을 2바이트 늘려야 하는데 바로 뒤 `$4253` 이 타일 데이터라
표를 통째로 옮겨야 한다. **어느 쪽이든 실기 검증 전에는 확정하지 말 것.**

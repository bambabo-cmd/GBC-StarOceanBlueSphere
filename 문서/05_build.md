# 빌드 파이프라인

```bash
python build.py [출력경로]
```

한 명령으로 검사 → 할당 → 빌드 → 검증까지 끝난다. 중간에 실패하면 즉시 멈춘다.

⛔ **`.ps1` 로 만들지 말 것.** Windows PowerShell 5.1 은 BOM 없는 UTF-8 스크립트를
CP949 로 읽어 한글 문자열을 깨뜨리고 파서 에러로 죽는다. 한 번 겪었다.

## 단계

| 단계 | 스크립트 | 하는 일 |
|---|---|---|
| 0 | `patch_font_engine.py` | 8 MiB 확장본에 **엔진 패치를 매번 다시 굽는다** |
| 0b | `audit_engine.py` | 미패치 사이트 0건 증명 |
| 1 | `check_tr.py` | 칸수 상한(이름 12 / 설명 17) 초과 검사 |
| 2 | `alloc_glyphs.py --incremental` | 문자 → 글리프 슬롯 배정 |
| 3 | `build_kr.py` | 폰트 주입 + 텍스트 재삽입 + 포인터 재계산 |
| 4 | `ptr_table.py dump` | 빌드본에서 포인터 테이블 재추출 |
| 5 | `verify_kr.py` | **새 인코딩으로 되읽어** 번역과 대조 |

⛔ **0단계를 손으로 만들어 둔 파일로 대체하지 말 것.** 엔진 패치를 고쳐도
빌드가 옛 베이스를 쓰면 반영이 안 된다 — 실제로 사이트 버그를 고친 뒤에도
그대로였다. 엔진 패치는 결정적이라 매번 굽는 비용이 사실상 없다.

5단계가 핵심이다. 빌드가 성공한 것과 게임이 읽을 수 있는 형태로 들어간 것은
다르다. 포인터가 가리키는 위치에서 실제로 그 한글이 나오는지 확인한다.

⛔ **단, 되읽기 검증은 인코더와 디코더가 같은 규약을 쓸 때만 의미가 있다.**
한때 둘 다 리드바이트를 `$5E`/`$5F` 뿐이라고 알고 있어서, 글리프 `0x5C` 에
「프」가 배정된 채 **429/429 일치**가 났다(엔진만 `0x5C` 를 리드로 봤다).
지금은 양쪽 다 `krcodec.iter_glyphs` 를 쓴다 — **규약 사본을 만들지 말 것.**

## 글리프 할당은 **증분이 기본**이다

⛔ 매 빌드마다 전체 재할당하면 음절이 1바이트 슬롯(0x60~0xFF)과 2바이트
슬롯(0x100~0x2FF)을 오가면서 **문자열 바이트 길이가 요동친다**. 넘치는 문장을
줄이면 다른 문장이 넘치는 식으로 끝나지 않는다(실제로 35→12→10→5 로
줄다가 다시 늘었다). `--incremental` 이 기존 배정을 고정해 이 진동을 끊는다.

전체 재할당은 슬롯이 바닥났을 때만 수동으로 한다.

### `--optimize` — 빈도 최적 재배치

슬롯 `0x000-0x0FF` 는 1바이트, `0x100` 이상은 2바이트로 인코딩된다. 그러니
**자주 쓰는 음절일수록 낮은 슬롯에** 있어야 텍스트가 짧아진다. 증분 배정만
반복하면 배정 순서가 굳어져 이 최적성이 무너진다.

```bash
python scripts/alloc_glyphs.py <tsv...> -o assets/glyph_alloc.json --incremental --optimize
```

⚠ **기본값이 아니다.** 매 빌드마다 돌리면 문자열 길이가 요동친다.
**번역이 크게 바뀐 직후에 한 번**만 돌린다. 2026-08-15 실측 445 B 절약.

### 넘치는 레코드는 문장이 아니라 배정으로 푼다

```bash
python scripts/fix_overflow.py assets/glyph_alloc.json out/items_overflow.tsv \
    --tsv assets/translations/items359.tsv --table items --all-tsv <전체 tsv...>

⛔ **아이템 표의 정본은 `items359.tsv`(359개) + `itemsA.tsv`(335개)** 다.
  269개 시절의 낡은 표가 `items_old269.tsv`·`items_old269b.tsv` 로 남아 있는데
  **키 접두사가 똑같이 `items:`** 라 이름만 보고는 구별이 안 된다(번호 체계가
  아예 다르다 — `items:0` 이 한쪽은 「エンゼルヘア」, 다른 쪽은 「ヴァリアント
  グリーブ」). 빌드는 `build.py` 의 `its` 목록에 적힌 둘만 쓴다.
```

그 레코드에 든 음절 하나를 1바이트 슬롯으로 올리고, 그 레코드에 **안 든**
음절 하나를 2바이트 슬롯으로 내린다. 전역 바이트는 조금 늘 수 있지만
넘치는 건 개별 레코드지 전체가 아니므로 이 교환이 옳다.
말줄임으로 문장을 깎는 것보다 언제나 먼저 시도할 것.

## 회수 금지 슬롯

`alloc_glyphs.py` 의 `CODE_USED` 에 박혀 있다. 근거는 `bankrefs.py` 전수 조사
(`docs/04_two_text_paths.md`). 텍스트 빈도만 보면 비어 보이지만 코드가 직접
주소를 박아 쓰는 구간이다.

## ⛔ 글리프 `0x100` / `0x200` 은 배정하면 안 된다

인코딩하면 `5E 00` / `5F 00` 이 되어 **뒷바이트 `0x00` 이 문자열 종단으로 읽힌다.**
그 자리에 배정된 음절이 든 문자열은 거기서 잘리고 뒤 필드가 통째로 밀린다.
실제로 「딥프리즈」가 잘려 6행이 어긋났고, 되읽기 검증이 잡아냈다.

## 테이블별 재삽입 정책

| 테이블 | 정책 | 이유 |
|---|---|---|
| 기술 (뱅크 `0x86`) | **재패킹 + 포인터 재계산** | 160엔트리 포인터 테이블이 레코드마다 있다 |
| 아이템 (뱅크 `0x31`) | **레코드 크기 보존** | 포인터가 카테고리 블록 단위(48개)인데, 그 블록 시작 48곳 중 **45곳이 우리 파서의 레코드 경계와 어긋난다**. 경계를 확신 못 하는 상태로 재배치하면 게임이 엉뚱한 위치를 읽는다 |

⛔ 기술 테이블을 **영역 상한까지 0 패딩하지 말 것.** `0x219B10` 뒤에 붙어 있는
별개 테이블(필드 능력)을 통째로 지운다. 원본 영역 크기까지만 채운다.

## 배포 패치는 BPS

ROM 이 8 MiB 로 커진 뒤로 **IPS 는 4.2 MiB** 가 된다 — 늘어난 4 MiB 를 그대로
레코드로 싣기 때문이다(IPS 는 압축도 출력 되참조도 없고, 24비트 오프셋이라
애초에 16 MiB 를 못 다룬다). **IPS 를 쓰지 말 것.**

BPS 는 `TargetCopy` 로 이미 쓴 출력을 되참조하므로 새로 붙인 4 MiB 의 0 런이
접힌다. 실측:

| 포맷 | 크기 |
|---|---|
| IPS | 4,200,000 B 남짓 |
| **BPS** | **32,317 B** (대상의 0.39 %) |

`build.py` 6단계가 빌드할 때마다 같이 만든다(빌드와 패치가 어긋나지 않게).
생성 직후 **그 자리에서 적용해 SHA-1 을 대조**한다.

## ⛔ 패치는 ROM 과 **다른 폴더**에 둔다

Mesen 을 비롯한 여러 에뮬레이터는 **ROM 옆에 같은 이름의 `.bps`/`.ips` 가 있으면
자동으로 덧씌운다.** 한때 `out/sobs_kr_wipNN.gbc` 와 `out/sobs_kr_wipNN.bps` 를
나란히 뱉었다 — **검수자가 실행한 것이 우리가 빌드한 것과 다를 수 있는 상태**였다.
증상이 재현되지 않거나 고친 것이 안 고쳐진 것처럼 보이면 이걸 먼저 의심할 것.

    out/    실행용 ROM (.gbc)   ← 여기엔 패치 파일이 있으면 안 된다
    dist/   배포 패치 (.bps)

`build.py` 가 마지막에 ROM 폴더를 훑어 같은 이름의 패치 파일이 있으면 **빌드를
실패시킨다**.

```bash
python scripts/bps_tool.py create <JP원본> <빌드본> -o patch.bps
python scripts/bps_tool.py apply  <JP원본> patch.bps -o out.gbc
python scripts/bps_tool.py info   patch.bps
```

⚠ 기준은 **JP 원본**이다(8 MiB 확장본이 아니라). 받는 사람이 가진 건 원본뿐이라
확장·엔진 패치·번역이 전부 패치 안에 들어가야 한다.
BPS 는 원본 CRC32 를 검사하므로 **다른 ROM 에 적용하면 거부된다**.

원본 ROM 이나 패치본 ROM 은 배포하지 않는다. 차분 패치만 배포한다.

## 빌드 뒤 — 구글드라이브에 쌓는다 (사용자 지시 2026-08-17)

**빌드할 때마다** 올린다. 배포 겸 **백업**이다.

```bash
python scripts/publish_drive.py   --stem "GBC StarOcean_bluesphere(SOBS) v0.8.1D_wip97_20260817"   --rom out/sobs_kr_wip97.gbc [--notes out/_notes.txt]
```

```
<프로젝트 폴더>/
  <이름>.gbc / .xdelta / .txt      배포 3종 — 판마다 쌓임
  작업백업/<이름>_작업파일.zip       docs·scripts·assets·build.py (롬 제외) — 판마다 쌓임
  문서/CLAUDE.md · docs/*.md       최신 상태로 갱신 (여기는 안 쌓는다)
```

⛔ **덮어쓰지 않는다.** 같은 이름인데 내용이 다르면 **빌드를 세운다** — 검수판을
계속 배포 중이라 「제보한 사람이 받은 판」을 그대로 재현할 수 있어야 한다.

⛔ **Drive MCP 로는 못 올린다.** 내용을 base64 로 실어 보내는 방식이라 8 MiB 롬이
**1,118만 자**가 된다. 탐색기에 마운트된 `G:` 로 **복사**한다. 복사 뒤 **SHA-1 로
대조**한다(동기화 중 잘린 파일을 그대로 두면 안 된다).

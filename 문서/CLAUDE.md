## ⛔ 작업은 영어로, **최종 보고는 한글로**

- **작업 언어 = 영어.** 사고·분석·중간 메모는 영어로 한다.
- **최종 결과 보고 = 한글.** 사용자에게 내보내는 마지막 요약은 한글로 쓴다.

자세한 것(경계 사례 포함)은 `docs/09_handoff.md` 맨 앞. (사용자 지시 2026-08-16)

**새 세션은 먼저 `docs/09_handoff.md`(핸드오프 — 지금 어디까지 왔나) 를 읽고,
그다음 `docs/01_initial_survey.md` → `docs/04_two_text_paths.md` →
`docs/07_remaining_text.md`(남은 텍스트 지도) 순으로 읽을 것.**

## 함정 (전부 실제로 밟은 것)

### ⛔ "빌드 성공 + 검증 통과 + 부팅 성공"인데 틀린 것들

이 프로젝트에서 가장 비싼 버그는 전부 이 부류였다. `docs/06_engine_patch.md`
§"검증이 통과하는 버그" 에 근거까지 적어 두었다.

- **인코더와 디코더가 규약 사본을 따로 들면 둘이 사이좋게 틀려도 검증이 통과한다.**
  글리프 `0x5C` 에 「프」가 앉은 채 되읽기 **429/429 일치**가 났다 — 패치된
  엔진만 `0x5C` 를 리드로 봤다. 규약 정본은 **`scripts/krcodec.py` 한 곳**.
- **코드가 값으로 글리프 인덱스를 계산하는 슬롯은 빈도 통계에 안 보인다.**
  숫자 `0x30-0x39` 에 「로」「시」「어」「약」이 배정돼 HP·소지금의 3/4/6/7 이
  한글로 나왔다. → `alloc_glyphs.PINNED`.
- **엔진 패치를 고쳐도 빌드가 옛 베이스 ROM 을 쓰면 반영이 안 된다.**
  → `build.py` 0단계가 매번 다시 굽는다.
- **폭 스캐너에 일괄 템플릿 금지** — 사이트마다 분기 극성이 다르고, `AND $FC`
  는 A 를 파괴하며, 8바이트 창이 `PUSH AF` 를 덮으면 스택이 깨진다.
- **사이트를 재작성하기 전에 `scripts/xrefs.py`** 로 그 내부 라벨로 들어오는
  바깥 분기가 없는지 확인할 것.
- **`CP $5E` 가 있다고 텍스트 엔진이 아니다.** ROM 전체 93건 중 진짜는 15건뿐
  (`CP $5F` 짝이 24바이트 안에 있는 것). 나머지는 장면 인덱스 비교나 데이터다.
- **3바이트 포인터의 셋째 바이트는 뱅크다.** 필러나 opcode 로 넘겨짚으면 엉뚱한
  표를 붙잡는다. 아이템 표를 `0x2F16CF`(뱅크 `0xEF`)로 잘못 알고 **269/359 개만**
  번역했고, 나머지 90개는 화면에 깨진 한글로 나왔다. 판별은 **뱅크 바이트가
  데이터의 뱅크와 같은지** 보면 끝난다.
- **⛔⭐⭐⭐ `glyph_swap` 으로 옮기면 안 되는 글자가 있다 — 파티원 이름.** (2026-08-18)
  파티원 이름은 ROM 이 아니라 **세이브(SRAM)에 있다**. 배정을 바꾸면 **기존
  세이브의 이름이 깨진다** — 「셀린」의 「셀」을 page0 으로 올렸다가 잡았다
  (화면에 「법린」이 나온다). 지금은 `glyph_swap` 이 `pcnames.tsv` 글자를 거부한다.
  ⭐ 교환 뒤에는 `make_savefix_html.py` 를 다시 굽고 **이름 바이트가 그대로인지**
  확인할 것. 자세한 것은 `docs/09` §0a-0w.
- **⛔⭐⭐ 제어코드가 「아무것도 안 한다」고 「안 쓴다」가 아니다.** (2026-08-18, wip116)
  텍스트 제어표 `$438F` 에서 `$43AF`(=`ret`)로 가는 칸이 여럿이지만 원본 대사가
  **실제로 쓴다**(`{0A}`1 `{0B}`2 `{0C}`5 `{0D}`1회). 조사 코드로 재활용하면
  그 대사에 글자가 튀어나온다. ⇒ 세는 방법도 함정이다 — **정규식으로 세면
  피연산자를 제어코드로 잘못 센다**(`{04}`·`{05}`는 1바이트를 먹는다).
  런을 **실제로 파싱해** 디스패치되는 것만 세면 0건은 `{06}`·`{09}`·`{0E}`·`{0F}` 뿐이다.
  자세한 것은 `docs/09` §0a-0v.
- **⛔⭐⭐⭐ 텍스트 런 시작을 한 바이트 앞으로 잡으면 게임이 즉사한다.** (2026-08-18, wip115)
  `1A 02 01 | 01 5B 05 …` 에서 앞의 `01` 은 **오퍼코드 `0x1A` 의 피연산자**인데
  훑기가 그걸 텍스트 오퍼코드로 봤다. 스텁 `85 FE …` 를 한 칸 앞에 쓰면
  `0x85` 가 피연산자로 먹히고 **뱅크 값 `0xFE` 가 오퍼코드로 실행**된다 ⇒
  점프표(135엔트리) 밖의 0 을 읽어 `jp $0000` → RST28→RST30 무한 재귀 →
  스택이 WRAM 을 덮고 정지/리셋. **빌드·되읽기 검증·부팅은 전부 통과한다.**
  ⇒ 판별자: **본문이 `{01}` 로 시작하면 틀린 것**이다(도달성 워크가 검증한
  5,470런 중 0건). 가드는 `evrepack` 에 있다. 자세한 것은 `docs/09` §0a-0u.
  ⚠ 원래 있던 `오퍼코드가 0x01 인가` 검사로는 **못 잡는다** — `01 01` 이라 둘 다 통과한다.
- **⛔⭐ 표 주소를 바이트 훑기로 짐작하지 말고 「읽는 코드」를 찾아라.**
  뱅크 57 제작 문구 표를 앞 세션이 `0x0E7A87`(홀수)로 적어 두었고 「홀수라서
  이상하다」는 주석까지 달려 있었다. 실제 표는 **한 엔트리 앞인 `0x0E7A85`** 다.
  `ld hl,$7A85` 한 줄이 답을 그냥 말해 준다. **이상하다고 느꼈으면 거기서
  멈추지 말고 한 칸 앞을 볼 것.**
- **⛔⭐ 표가 안 가리키는데 화면에는 나오는 문자열이 있다 — 코드가 즉치로 잡는다.**
  같은 표의 공통 꼬리 `$7BCE`「を…えらんで下さい」가 그랬다. `ptrpool` 의
  자기증명(표+문자열==영역)이 **정확히 그 11바이트만큼 어긋난다** —
  이때 「구조를 덜 이해했다」로 결론 내면 표 전체를 포기하게 된다.
  ⇒ **남는 바이트를 디코드해 보고, 그 주소를 담은 즉치(`21 lo hi`)를 찾아라.**
    찾으면 `ptrpool` 의 `imm` 로 등록한다(자기증명에 더하고 즉치도 같이 고친다).
  ⚠ `places2` 가 아직 이 상태다(11 B 가 남는데 즉치를 못 찾았다).
- **⛔ 즉치로 참조하는 쪽이 「고정 길이 복사」를 하기도 한다.** 이 꼬리는
  `LD BC,$0040` 으로 **64바이트를 통째로** 읽는다. NUL 뒤는 버려지지만
  읽기는 하므로, 옮긴 자리 + 64 가 `$8000` 을 넘으면 **VRAM 을 읽는다.**
- **표를 찾았으면 그 표의 앞뒤를 마저 볼 것.** 아이템 포인터 표는 **둘**이었다
  (`0x0C8472` 335개 뱅크 `0x30` + `0x0C885F` 359개 뱅크 `0x31`, 합계 694개).
  둘이 바이트로 붙어 있는데 뒤 표만 보고 "아이템 표를 찾았다"고 넘어가서
  **앞의 335개(텔레포터·몬스터도감·각종 열쇠 같은 핵심 아이템)를 통째로**
  번역 안 한 채 두 달을 보냈다. 발견 계기도 우연이었다 — 판독표를 고치다가
  「一度しか使えないカギ」가 아이템 표 **밖**에 있는 걸 봤다. (2026-08-15)

- **⛔⭐⭐⭐ 「마지막 비영 바이트 + 1」은 빈 칸이 아니다 — 문자열의 NUL 종단자다.** (2026-08-19)
  치트 훅을 뱅크13 `$794A` 에 넣었더니 전멸 메시지가 **「…전멸했다…티사군요（」**
  로 나왔다. 화면에 찍힌 것은 `FA 6B C1 B7` = **`ld a,($C16B) / or a`** — 우리 코드다.
  꼬리의 마지막 비영 바이트가 `$7949`(글자)였고 **`$794A` 는 그 문자열의 종단자**였다.
  ⚠ 「구간이 전부 0x00 인가」 검사는 **통과한다** — 종단자도 0x00 이기 때문이다.
  ⚠ 원본(JP)에서는 그 꼬리가 진짜로 비어 있었다. **번역이 문자열을 그리로 옮겨 놓아서**
  KR 빌드에서만 생긴다 ⇒ **베이스 ROM 이 아니라 번역된 ROM 으로 여백을 재야 한다.**
  ⇒ `patch_cheat` 는 이제 시작 앞 **4 B 가 전부 0x00 인지**까지 본다(`MARGIN`).
  ⭐ 뱅크7 은 마지막 비영이 `C9`(=`ret`, 코드)라 종단자가 없어 원래도 안전했다 —
  즉 **앞이 코드냐 문자열이냐로 갈린다.** 기계로 구분이 안 되니 여백을 두는 게 답이다.
- **⛔⭐⭐⭐ 세이브를 고쳤으면 「체크섬」도 다시 계산해야 한다.** (2026-08-19)
  이름만 고친 세이브를 넣었더니 게임이 **「데이터가 손상되었습니다」로 거부**했다.
  ⇒ **사용자 세이브를 깨뜨렸다.** 뱅크1 `$787F` 가 검사하고 `$7959` 가 센다:
  ```
  DE = 0 ; HL = $A000 ; BC = $1E00 ; loop: DE += (HL) ; HL++ ; BC--
  ```
  ⇒ SRAM 뱅크의 **`0x0000~0x1DFF` 7,680 B 를 16비트로 더한 값**을 같은 뱅크
  **`0x1F00`** 에 리틀엔디안으로 넣는다(`$BF00` 과 비교). 대상은 **SRAM 뱅크 1·2**.

  화면 전체에 8픽셀마다 초록 가로줄이 깔렸고 **빌드·되읽기 검증·부팅이 전부
  통과했다**. → 경계의 정본은 `scripts/make_pools.py` 의 `POOLS`, 가드는
  `build_kr` 의 "슬롯이 `end` 를 넘으면 빌드 실패".
  ⛔ `out/pool_*.json` 을 손으로 만들어 두고 쓰지 말 것 — `out/` 은 git 에 없어서
  **경계가 어디에도 기록되지 않는다.** build.py 0d 단계가 매번 다시 뽑는다.
- **`[뱅크 바이트][2B 포인터 × N]` 표가 한 뱅크에 여러 벌 이어져 있다.**
  뱅크 134 를 "기술 표 160엔트리 하나"로 알고 있었지만 실제로는 표가 6개였고
  **230 레코드가 통째로 미번역**이었다(`docs/07`). 훑을 때 다음 표의 뱅크
  바이트(`0x86`)를 포인터 첫 바이트로 먹으면 허깨비 엔트리가 하나 생긴다.
- **⛔⭐ 리드바이트로 쓸 값은 원본에서 몇 번 쓰이는지 반드시 세라. (2026-08-16, 고침)**
  1단계 확장이 page3 리드로 `$5D` 를 가져갔는데 원본에서 `$5D` 는 **`』`** 다.
  `『…』` 인용의 닫는 짝이라 스크립트에 **597번** 나온다. `krcodec` 주석은
  「확장의 대가로 `¥`·`』` 를 포기한다」고 적어 두었지만 **몇 번 쓰이는지를
  아무도 세지 않았다**(2단계 후보 `$59`·`$5A`·`$5B` 만 실측했다).
  ⇒ 미번역 문자열의 `』` 가 리드로 읽혀 **뒷바이트를 먹었다**. 증상 둘이 한 뿌리:
    1. 글자가 엉뚱한 한글로 깨진다
    2. **먹힌 바이트가 `{01}`·`{03}` 이면 줄바꿈·쪽넘김이 사라져 「대기 없이
       다음으로 넘어간다」** — 실측 27줄. **사용자 제보로 잡혔다.**
  ✅ **고쳤다**: page3 `$5D`→`$5A`(26B), page4 `$5C`→`$59`(27B). 피해 457B→53B.
  ⛔ `$5B`(『, 507회)는 계속 건드리지 않는다.
  ⚠ 번역이 끝난 줄은 저절로 낫지만 **우리 표 밖의 텍스트**(오프닝 데모 대사)는
  깨진 채다 — 그 표는 아직 못 찾았다.
  → 가드: `scripts/lead_route.py` 가 사이트를 **A=0x00~0xFF 전수 시뮬레이션**해
  원본과 대조한다(`build.py` 0b3). 이 검사가 `$4F3C`·`$5480` 의
  **「0x60 이상이 전부 리드로 샌다」는 기존 버그**도 잡았다.
- **⭐ 번역문에 원본 ASCII 글자를 새로 들이면 그 슬롯에 앉아 있던 한글이 쫓겨난다.**
  `alloc_glyphs` 는 **원본 슬롯 유지(keep)를 회수 배정보다 우선**한다. 대사에
  「OK！」를 써서 `K` 가 처음 필요해졌더니, `K` 가 원래 자리 **슬롯 75**를
  되찾고 거기 앉아 있던 **「가」가 페이지4(1188)로 밀렸다.** 「가」는 한 글자가
  1바이트에서 **2바이트**가 되고, 그 한 바이트 때문에 **전혀 상관없는 UI 표**
  (`sysmsg` `itemfx`)가 줄줄이 길이 초과로 빌드에 실패한다.
  → 원인을 표에서 찾지 말고 **`git diff assets/glyph_alloc.json` 으로 옮겨간
  글자를 먼저 본다**(옮긴 글자가 딱 하나였다). 흔한 음절이 페이지3+ 로 갔으면
  그게 범인이다. 고치는 쪽은 **새로 들인 ASCII 글자를 안 쓰는 것**이 제일 싸다
  (「OK！」→「좋아！」). 그리고 **`glyph_alloc.json` 을 되돌린 뒤** 다시 빌드해야
  한다 — 증분 할당이라 한 번 밀린 배정은 저절로 안 돌아온다. (2026-08-16)
- **⭐⭐ 「이 사이트는 page0 만 쓴다」는 판정을 믿지 말 것 — 표가 바뀐다.**
  캐릭터 리포트 이름표(`0x2C6A5A`, 뱅크 177)는 `LD H,$00` 으로 0~255만 그리는데,
  예전 세션이 「베이스가 `LD DE,$4001` 고정이고 리드 판정이 없으니 page0 전용」
  이라 적고 **뱅크 즉치만 바꾸고 넘어갔다**. 그런데 `chnames` 12개 중 **10개가
  2바이트 글리프**를 쓴다 ⇒ 리드바이트 `$59` 가 글리프로 읽혀 화면에 **원본 `Y`**
  가 나오고 뒤 글자가 밀렸다(「오페라・벡트라」→「오페라・Y○트」).
  ⛔ 사용자 제보로 잡혔다 — **빌드·검증·부팅이 전부 통과한다.**
  ⇒ 판정은 「지금 그 표가 page0 만 쓰나」가 아니라 **「이 렌더러가 리드를 아나」**다.
- **⭐⭐ 「표」에 안 들어가는 1~3글자 조각 문자열이 화면에 나온다.**
  조사·단위·구분자는 코드가 즉치(`LD HL,$xxxx`)로 잡는 **아주 짧은 문자열**로
  따로 놓여 있다. 실기에서 잡은 둘:
  - `0x007631` **`":"` 1바이트** — 세이브 화면 시간 구분자 (「30로57로16」)
  - `0x00E55E` **`"の"` 1바이트** — 스킬 화면 「<이름>の」 (「합의불군유」)
  `make_pools` 의 `minlen` 기본값 3 이 이런 걸 통째로 거른다 — **1 로 내려야** 잡힌다.
  ⚠ 아직 안 본 후보: 「を」(0x0303D7·0x0306F1) 「から」「に」(0x012AD1·4)
  「かい」「てん」「ほん」(0x03D1FD·0x03D200·0x03EE5F).
- **⭐ 회수하면 안 되는 슬롯은 숫자만이 아니다 — `:` 도 그랬다.** 세이브 화면의
  플레이 시간 구분자는 뱅크 1 `0x007631` 의 **1바이트 문자열 `":"` 하나**이고
  코드가 그걸 두 번 그린다. 슬롯 `0x3A` 를 「로」에 내줬더니 화면에
  **「30로57로16」** 이 나왔다(2026-08-17 실기 QA, 사용자 제보).
  ⛔ 판정이 안 보이는 이유가 숫자와 똑같다 — **번역 TSV 어디에도 `:` 가 없으니
  빈도 통계로는 영원히 안 잡힌다.** → `alloc_glyphs.PINNED` 에 올렸다.
  회수했던 「로」(빈도 2,009)는 **page0 안에서 교환**했다(「로」↔「채」).
- **"빈 슬롯"이라는 판정을 믿지 말 것.** `glyph_usage.py` 는 **우리가 추출한
  블록만** 센다. 추출 안 한 텍스트가 참조하는 슬롯은 "빈 칸"으로 보인다.
  실제로 메인 메뉴가 `0x13C~0x13F` 로 「ステータス」를 그리는데 거기 한글을
  배정해 메뉴 항목이 깨졌다. → `CODE_USED` 에 `0x13A-0x13F` 추가.

### 그 밖

- **폰트 베이스는 `0xF4000` 이 아니라 `0xF4001`** (뱅크 첫 바이트 = 뱅크 ID).
- **글리프 `0x100`/`0x200`/`0x300` 배정 금지** — 인코딩하면 뒷바이트가 `0x00` 이라
  문자열이 끊긴다.
- **⭐ 자리가 1~2바이트 모자라면 `scripts/glyph_swap.py` 를 먼저 돌린다.**
  page0 은 1바이트, page1+ 는 2바이트인데 **지금 배정은 빈도순이 아니다**
  (증분 할당이라 먼저 들어온 글자가 page0 을 차지했다). 그래서 「글자 수는
  맞는데 바이트가 넘친다」가 흔하다. 빡빡한 표에서 **빈도 0 인 page0 한글**과
  맞바꾸면 **공짜다**. 도구가 후보를 뽑아 주고, 내보내는 글자가 빡빡한 표에
  쓰이면 **거부**한다(그러면 그 표가 대신 넘친다).
  ⇒ `monpart` 가 1 B 모자랐을 때 「코」↔「열」 로 풀었다 — 「코」가 빡빡한 표에서
    12회 쓰여 **다른 표들도 같이 가벼워졌다**.
- **넘치는 레코드는 문장을 깎기 전에 글리프 배정을 바꿔 본다.**
  ⭐ 「글자 수는 맞는데 바이트가 넘친다」가 흔하다 — page1+ 음절은 **2바이트**다.
  **빡빡한 표(`make_pools.POOLS`+`monname`)에서 빈도 0인 page0 한글이 30자** 있으니
  그중 하나와 맞바꾸면 공짜다. 실제로 「アクア」(3 B) 자리에 「아쿠아」(4 B)가 안 들어가
  「쿠」↔「벤」을 교환해 넣었다(2026-08-17). 비용은 여유 있는 표가 흡수한다.
- **글리프 할당은 증분(`--incremental`)** — 매번 재할당하면 문자열 길이가 요동쳐
  "문장 줄이기"가 끝나지 않는다.
- **기술 테이블을 영역 상한까지 0 패딩 금지** — 뒤의 필드 능력 테이블을 지운다.
- **⛔⭐⭐ 「닫는 짝인 건 아는데 이름은 딴 걸로」 — `0x5D` 를 3개월 동안 ♪ 로 불렀다.**
  실제 글리프는 **`』`(닫는 겹낫표)** 다. 비트맵이 겹선 모서리이고, 원문에서
  `『` 479개 / `0x5D` 478개로 **짝이 맞는다**. 그런데 문서에는
  「`『…♪` 인용의 **닫는 짝**이라 597번 나온다」고 — **닫는 짝인 걸 알면서도**
  이름만 ♪ 로 적혀 있었다. 우리 글꼴이 그 이름대로 **음표를 그려서** 화면에
  「『오페라 맞아！？♪」로 나왔다(검수 제보 2026-08-17, wip87 에서 고침).
  ⇒ **판독 이름과 그 글자가 하는 일이 어긋나면 이름이 틀린 것이다.**
    번역 1,549군데를 ♪→』 로 바꿨다.
- **판독은 낱개 비트맵으로 하지 말 것** — `kanji_sheet.py` 로 단어 문맥 안에서 본다.
  비트맵만 보고 `1F8`을 殺로 넣었다가 디코드 문맥(`殺{147}{217}`)으로 잡았고,
  `2BB/2BC`를 「基本」으로 읽었다가 「料理」로 정정했다(「料理人」으로 확정).
- **한 문맥에서만 그럴듯한 판독은 오독이다.** 새 표를 열 때마다 기존 판독표를
  다시 검증하게 된다 — 새 문맥이 반례를 준다. 2026-08-15 필드 액션 표에서
  세 글자가 뒤집혔다: `27E` 暗→**禁**, `27F` 黒→**断**, `23B` 斬→**切**.
  「暗黒の魔力」만 보면 그럴듯했지만 「ゆがみは暗物です」가 말이 안 됐고,
  다시 렌더해 보니 禁(林+示)이었다(「禁断の魔力」·「禁物」 둘 다 성립).
  → **미지 글리프를 읽을 때 그 글리프가 쓰인 다른 문맥을 전부 같이 볼 것.**
- **라운드트립은 필드 배정 오류를 못 잡는다** — 읽은 걸 그대로 되쓰니 바이트는 맞다.
  내용을 눈으로 봐야 드러난다(아이템 103번 이후 이탈이 그랬다).
- **`.ps1` 로 스크립트를 만들지 말 것** — PowerShell 5.1 이 CP949 로 읽어 한글이 깨진다.
- **MENU/HELP/フォル/파티원 이름은 폰트가 아니라 그래픽**(`0xF7001~`). 폰트 슬롯을
  뒤져도 안 나온다.

## 배포 버전 규칙 (사용자 지시 2026-08-17)

```
v0.8.1E
  │ │ │└ 알파벳 = 작은 변화(텍스트 몇 개)
  │ │ └── 셋째 자리 = 그보다 중요한 변화(로직·대사 수백)
  │ └──── 둘째 자리 = 대규모 판
  └────── 검수 종료 시 0.9~1.0 에서 정식판 번호를 고른다
```

- ⛔ **숫자를 올릴 때는 알파벳을 뗀다** — `v0.8.1E` 다음은 `v0.8.2A` 가 아니라
  **`v0.8.2`** 다. 알파벳은 새 숫자 자리에서 다시 A 부터 쌓는다.
- ⛔⭐ **알파벳은 「셋째 자리」에만 붙는다** (사용자 지시 2026-08-18).
  ```
  v0.9  →  v0.9.1  →  v0.9.1A  →  v0.9.1B  → …  →  v0.9.2  →  v0.9.2A
                                                    ↑ 숫자 올렸으니 알파벳 뗌
  ```
  ⇒ **`v0.9A` 는 없는 꼴이다** — 둘째 자리에 알파벳을 붙이면 셋째 자리를 통째로
  건너뛴 것이다. 실제로 `v0.9` 다음을 `v0.9A`~`v0.9G` 로 **일곱 번** 올려 버렸다
  (2026-08-18). 지금은 `publish_drive` 가 막는다.
- ⛔⭐⭐⭐ **기본은 알파벳만 올린다. 숫자는 사용자가 말해 줄 때만.**
  (사용자 지시 2026-08-18)
  ```
  v0.9.3  →  v0.9.3A  →  v0.9.3B  →  …        ← 에이전트는 여기까지만 한다
                       ↑ 사용자가 「0.9.4 로 올려」 하면 그때 숫자를 바꾼다
  ```
  에이전트가 알아서 숫자를 올리다 하루에 v0.9 → v0.9.1 → v0.9.2 → v0.9.3 까지
  갔다 — 이 속도면 검수가 끝나기도 전에 **1.0 에 닿는다**(정식판용 자리다).
  ⚠ **wip121 = `v0.9.3`** 이 기준점이다. 다음 배포는 `v0.9.3A`.
  ⚠ 사용자가 직접 올린 판이 있을 수 있다(wip118 = `v0.9.2A`) — **이름이 겹치지
  않게** 드라이브 루트를 먼저 확인할 것.
- ⛔ **배포(드라이브 업로드)마다 버전이 올라간다.** `v0.8.1D` 로 다섯 판을
  연달아 올린 적이 있다 — `release.check_not_backwards` 는 **거꾸로 가는 것**만
  봤기 때문이다. 지금은 `publish_drive.check_version_advanced` 가 막는다.
- 정본은 저장소 루트의 **`VERSION`** 파일이다(환경변수 `SOBS_VERSION` 이 우선).
- 빌드·업로드:
  ```bash
  python build.py out/sobs_kr_wipNN.gbc
  python scripts/publish_drive.py --stem "<배포이름>" --rom out/sobs_kr_wipNN.gbc
  ```
- ⛔ **드라이브 루트에는 배포판만 올린다** (사용자 결정 2026-08-17). 검수자가 보는
  곳이 루트라, 중간 빌드를 같이 쌓으면 어느 것이 검수판인지 헷갈린다.
  중간 빌드는 **`--dev`** 로 `작업백업/중간빌드/` 에 쌓는다(버전 올림 검사 면제).

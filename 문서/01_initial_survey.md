## 1. 매체 (사실)

| 항목 | 값 |
|---|---|
| 파일 | `Star Ocean - Blue Sphere (Japan).gbc` |
| 크기 | 4,194,304 B = 4 MiB = 256 뱅크 |
| SHA-1 | `3D07AE53BA21EDA4923BF4DA6C938E2A407C990C` |
| MD5 | `820E0A19275FABC03FE619C42DB47179` |
| CRC32 | `8C7DDBDA` |
| 타이틀 | `STAROCEANGBBO2J` |
| CGB flag | `0x80` (CGB 지원, DMG 호환) |
| 카트리지 타입 | `0x1B` = **MBC5 + RAM + BATTERY** |
| ROM size 바이트 | `0x07` (4096 KiB) / RAM `0x03` (32 KiB) |
| 헤더 체크섬 | stored `0x60` = calc `0x60` OK |
| 글로벌 체크섬 | stored `0x1571` = calc OK (런타임 미검증) |

**확장 가능성 (사실)** — MBC5는 ROM 뱅크 레지스터가 9비트(`0x2000` 하위 8비트 + `0x3000` 비트 8)라
최대 512뱅크 = **8 MiB** 를 지원한다. 헤더 `0x148` 을 `0x08` 로 올리고 뒤에 256뱅크를 덧붙이면
4 MiB 의 신규 공간을 얻는다. (실기 플래시카트 호환은 미검증 — 가설)

## 2. 폰트 (사실 — PoC로 확증)

| 항목 | 값 |
|---|---|
| 위치 | **`0xF4001`** (뱅크 `0x3D`, CPU `0x4001`) |
| 끝 | `0xF7001` |
| 글리프 수 | **768개 (인덱스 `0x000`~`0x2FF`)** |
| 포맷 | GB 2bpp 타일, **16 B/글리프**, 8×8 |
| 특징 | lo 플레인 == hi 플레인 (사실상 1bpp를 2bpp로 저장) |

영문 버그픽스 패치가 `0x0F41B1`(글리프 `0x1B`)부터 `0x0F7001`(글리프 `0x300`)까지 덮어쓴 것과
정확히 일치한다 → 이 영역이 폰트 시트임의 교차 증거.

### 2.1 글리프 배열 (사실, 시트 렌더 `out/jp_font_sheet.png`)

| 인덱스 | 내용 |
|---|---|
| `0x00`~`0x1F` | 제어/괘선·기호 (텍스트 스트림에서는 제어코드로도 쓰임) |
| `0x20`~`0x2F` | 공백·기호 (`! " … % · × ( ) ✱ + 、 ー ・ /`) |
| `0x30`~`0x3F` | `0`~`9` `:` `ヴ` `<` `=` `>` `?` |
| `0x40`~`0x4F` | `@` `A`~`O` |
| `0x50`~`0x5D` | `P`~`Z` `『` `¥` `』` |  ⛔ 2026-08-17 정정: `0x5D` 는 ♪ 가 아니다
| **`0x5E` / `0x5F`** | **한자 리드 바이트** (§3 참조) |
| `0x60`~`0xBF` 부근 | 히라가나 (**탁음·반탁음이 5자 그룹 사이에 끼어 있음**) |
| ~`0x11F` 부근 | 가타카나 |
| `0x120`~`0x2FF` | 한자 (약 480자) |

히라가나 배열 확정분(실측): `あ60 い61 う62 え63 お64 / か65 き66 く67 け68 こ69 /
が6A ぎ6B ぐ6C げ6D ご6E / さ6F し70 す71 せ72 そ73 / ざ74 じ75 ず76 ぜ77 ぞ78 /
た79 ち7A つ7B て7C と7D / だ7E ぢ7F …`

전체 판독표는 `docs/02_charmap.md` 에서 관리한다(작성 중).

### 2.2 두 번째 시트 (가설)

뱅크 `0x3E`(`0xF8001`) 를 `LD A,$3E` 로 참조하는 코드가 최소 2곳
(`0x3C014` → VRAM `$9200`, `0xE6A83` → VRAM `$9740`). 레코드 크기가 **144 B(=9타일)** 로 계산되어
본문 폰트가 아니라 얼굴 아이콘/특수 그래픽으로 추정. 미확정.

## 3. 텍스트 인코딩 (사실 — VRAM↔ROM 대조로 확증)

**가변장 1~2바이트, 글리프 인덱스 직접 참조.**

| 바이트 | 의미 |
|---|---|
| `0x00`~`0x1F` | 제어코드 (`0x01` = 개행 — 실측 확인) |
| `0x20`~`0x5D` | 글리프 인덱스 그대로 |
| **`0x5E xx`** | 글리프 **`0x100 + xx`** |
| **`0x5F xx`** | 글리프 **`0x200 + xx`** |
| `0x60`~`0xFF` | 글리프 인덱스 그대로 |

검증 근거 — 오프닝 대사 `0x2C4D04`(뱅크 `0xB1`) 의 바이트열과 화면 VRAM 글리프 인덱스가 일치:

```
ROM : 5e 81 5f 72 63 61 72 61 cc cd ef c5 fa d6 c1 84 71 99 01 …
해석: 人(181) 工(272) え い せ い テ ト ラ ジ ェ ネ ス (084)(071)(099) [개행] …
화면: 181 272 063 061 072 061 0CC 0CD 0EF 0C5 0FA 0D6 0C1 084 071 099 …
```

**스크립트는 비압축**으로 저장된다(사실). 같은 오프닝 텍스트가 `0x2C4D04` 와 `0x2C5457` 두 곳에 중복
존재 → 언어/연출 분기 또는 재사용 (미확정).

## 4. 렌더 경로 (부분 확정)

- 글리프는 **ROM 폰트 시트에서 VRAM 타일로 그대로 복사**된다. VRAM 타일 바이트가 ROM 폰트 바이트와
  **바이트 단위로 동일**함을 확인(사실). 즉 VWF(가변폭 합성)가 아니라 **8×8 고정폭 타일 블릿**.
- 대화창 경로는 팔레트 재색칠을 한다: VRAM 타일의 hi 플레인 = 글리프 마스크, lo 플레인 = `0xFF`(배경색).
- 뱅크 지정 복사 서브루틴 **`$06FD`** (실측: `A`=뱅크, `HL`=소스, `DE`=목적, `BC`=길이).
  유사 루틴 `$0D83` 도 존재. 부팅 시 폰트 일부를 VRAM 에 벌크 프리로드하는 호출이 여러 곳:
  - `0x00C048` (뱅크3): `LD HL,$4001 / LD DE,$9000 / LD BC,$0010 / LD A,$3D / CALL $0D83`
  - `0x004576` (뱅크1): 같은 형태, `BC=$0200`(32글리프)
- **미확정**: 대사 1글자를 인덱스로 받아 폰트 주소를 계산하는 루틴의 위치. ROM read 브레이크포인트가
  잡히지 않아 GDMA 또는 다른 경로 의심. → 폰트 시트를 768글리프 이상으로 확장할 때 반드시 확정해야 함.

## 5. PoC 게이트 (통과)

**최소 가시성 PoC — 통과 (2026-08-14).**

`scripts/poc_glyph.py` 로 JP 원본의 글리프 슬롯 `0x60`~`0x64`, `0x181` 을 갈무리7(Galmuri7, OFL)
8×8 래스터 한글(`한 글 패 치 다 사`)로 덮어쓴 ROM 을 Mesen2(emucap)에서 구동.

- 게임 정상 부팅, 인게임 대화창 진입
- VRAM 타일 `0x9B` 의 바이트 = `7c7c0404fefe7c7c1c1c60607c7c0000` = 주입한 `글` 비트맵과 **완전 일치**,
  ROM 역검색 결과 `0xF4611`(글리프 `0x61`) → **게임의 원래 데이터 경로를 통해 한글이 화면에 표시됨**

증명된 것: 폰트 시트 위치·포맷·엔디안, 렌더 경로가 ROM 폰트를 그대로 쓴다는 것, 8×8 한글의 가독성.
증명되지 않은 것(조건부 게이트로 분리): 글리프 수용량 확장, 인코딩 공간 확장, 포인터 재배치.

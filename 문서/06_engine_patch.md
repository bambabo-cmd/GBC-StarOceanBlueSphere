# 폰트 엔진 확장 패치

목표: 글리프 상한 **768 → 1024** (페이지 4개, 단일 뱅크 `0xFA`).
원본은 베이스 주소를 코드에 하드코딩해서 `$6FF1`(글리프 `0x2FF`)를 넘지 못한다.

**상태: 완료.** 사이트 15곳 전부 패치, `scripts/audit_engine.py` 미패치 0건.

## 확정된 원본 구조

### 글리프 주소 계산 (대표 사이트 `0x000F87`)

```
0F87  11 01 40   LD DE,$4001        ; page0
0F8A  FE 5E      CP $5E
0F8C  20 06      JR NZ,$0F94
0F8E  2A         LD A,(HL+)         ; 리드바이트면 다음 바이트를 먹는다
0F8F  11 01 50   LD DE,$5001        ; page1
0F92  18 08      JR $0F9C
0F94  FE 5F      CP $5F
0F96  20 04      JR NZ,$0F9C
0F98  2A         LD A,(HL+)
0F99  11 01 60   LD DE,$6001        ; page2
0F9C  E5         PUSH HL
0F9D  CB 37 …    SWAP/AND/…         ; HL = DE + A*16
0FA7  19         ADD HL,DE
0FA9  11 00 88   LD DE,$8800        ; VRAM 목적지 계산
0FBF  C5         PUSH BC
0FC0  06 3D      LD B,$3D           ; ← 폰트 뱅크
0FC2  CD DD 06   CALL $06DD         ; 뱅크 B:HL → DE 로 16바이트 복사
```

### 복사 루틴 `$06DD`

```
06DD  FA 00 40   LD A,($4000)   ; 현재 뱅크 = **뱅크 첫 바이트에 박힌 번호**
06E0  F5         PUSH AF
06E1  78         LD A,B
06E2  EA 00 20   LD ($2000),A   ; MBC5 뱅크 하위 8비트만 쓴다
```

⛔ **뱅크 규약**: 이 게임은 각 뱅크 첫 바이트에 자기 뱅크 번호를 둔다
(원본 242/255 뱅크에서 확인, 불일치 13개는 전부 빈 뱅크).
폰트가 `0xF4000` 이 아니라 `0xF4001` 에서 시작하는 이유가 이것이다.
**새로 만드는 뱅크도 반드시 각인해야 한다.**

⛔ `LD ($2000),A` 뿐이라 **뱅크 `0x100` 이상은 원본 코드로 도달 불가**.

### 텍스트 포인터 전진 `$40B9` (뱅크14)

```
40B9  PUSH HL / PUSH BC
40BB  LD HL,$CF43 → B=뱅크, HL=($CF41/42) 현재 포인터
40C3  CALL $2F0D              ; 뱅크 B 의 (HL) 을 읽어 A 로
40C6  INC HL
40C7  BIT 7,H / JR Z,$40D2    ; $8000 을 넘었나?
40CB  LD HL,$CF43 / INC (HL)  ; 넘었으면 뱅크 +1
40CF  LD HL,$4001             ; ← 다음 뱅크의 **둘째 바이트**부터 (첫 바이트는 뱅크 ID)
40D2  ($CF41/42) 갱신 / A=B / POP / RET
```

`DE` 를 보존한다(원본이 `LD D,$50` 뒤에 이걸 부르므로 성립해야 한다).

⛔ **`0x0380CF` 의 `LD HL,$4001` 은 폰트 베이스가 아니다** — 위의 뱅크 넘김
처리다. 근처에 `CP $5E` 가 있어 베이스 사이트로 오인되며, 예전 문서는
실제로 이걸 "손댈 10곳"에 넣어 두었다. **고치면 텍스트 포인터가 깨진다.**

## 리드바이트 규약

| 페이지 | 리드 | 글리프 | 베이스 |
|---|---|---|---|
| 0 | (없음) | `0x000-0x0FF` | `$4001` |
| 1 | `$5E` | `0x100-0x1FF` | `$5001` |
| 2 | `$5F` | `0x200-0x2FF` | `$6001` |
| 3 | `$5D` | `0x300-0x3FF` | `$7001` |
| — | `$5C` | (page3 별칭, 미사용) | `$7001` |

패치된 코드는 전부 **범위비교**(`CP $5C` / `CP $60`)를 쓰므로 엔진은
`$5C~$5F` **넷 모두**를 리드로 본다. 원본에서 `$5C`=¥ `$5D`=』 는 표시
문자였다 — 확장의 대가로 그 둘을 포기한다.

⛔ 그래서 **글리프 슬롯 `0x5C~0x5F` 에 음절을 배정하면 안 된다**
(`krcodec.RESERVED_LEADS`). 실제로 `0x5C` 에 「프」가 배정된 채 빌드·검증을
통과했다 — §"검증이 통과하는 버그" 참조.

규약 정본은 **`scripts/krcodec.py` 한 곳**이다. 인코더/디코더/할당기가
각자 사본을 들면 셋이 사이좋게 틀려도 검증이 통과한다.

## 패치 설계

핵심: **헬퍼가 ROM0 여유공간(`$3B16-$4000`, 1258 B)에 살고, 사이트는
`CALL 헬퍼` + 패딩으로 바뀐다.** 뱅크는 상수로 고정하므로(`LD B,$3D` →
`LD B,$FA`) 레지스터 운반 문제가 통째로 사라진다.

### 헬퍼 6종 (총 196 B, `$3B20-$3BE3`)

| 헬퍼 | 쓰는 사이트 | 하는 일 |
|---|---|---|
| `h_de_fetch` | 뱅크0 4곳 | `D` 갱신 + `LD A,(HL+)` |
| `h_d_only` | `0x03A3E7` | `D` 만 갱신 (둘째 바이트가 이미 A 밖에 있음) |
| `h_p_bank14` | `0x039AA7` | `D` 갱신 + `JP $40B9` — ⛔**뱅크14 전용** |
| `h_de_b` | `0x0388C6` | `DE` 전체 + 리드면 `A=B` |
| `h_hl_cnt` | `0x034401` | `HL`=베이스, `A=(HL)`, **`$D5A0` 카운터 증가** |
| `h_bc_de` | `0x2C6D26` | `BC`=베이스, `A=(DE)`, `DE` 전진 |

⚠ `h_p_bank14` 의 `JP $40B9` 는 **뱅크 14 가 매핑돼 있을 때만** 유효하다.
ROM0 에 살지만 뱅크14 사이트에서만 불린다는 전제가 깨지면 엉뚱한 곳으로 뛴다.

⚠ `h_hl_cnt` 는 **`DE` 를 건드리면 안 된다** (`$4426 PUSH DE` / `$4431 LD A,D`).
`B` 는 바로 뒤 `LD B,H` 로 덮이므로 스크래치로 안전하다.

⚠ `$D5A0` 카운터는 "리드바이트를 소비했다"를 상위에 알리는 값이다.
빠뜨리면 글자는 맞고 **줄 폭·커서 위치만 틀어진다**.

### 사이트 전수 (15곳)

**베이스 생성 9곳**

| 오프셋 | 뱅크 | 형태 | 처리 |
|---|---|---|---|
| `0x000F87` `0x001002` `0x001078` `0x0010E3` | 0 | `LD DE,$4001` | `h_de_fetch` |
| `0x03A3E7` | 14 | `LD D` 만 | `h_d_only` |
| `0x039AA7` | 14 | `LD D` + `CALL $40B9` | `h_p_bank14` |
| `0x0388C6` | 14 | `LD DE` + `A=B` | `h_de_b` |
| `0x034401` | 13 | `HL` 재사용 + `$D5A0` | `h_hl_cnt` |
| `0x2C6D26` | 177 | `BC` 베이스, `DE` 포인터 | `h_bc_de` |

**폭 스캐너 6곳** (베이스는 안 만들고 "리드는 2바이트"만 아는 곳)

| 오프셋 | CPU | 크기 | 리드 목적지 | 비리드 목적지 |
|---|---|---|---|---|
| `0x00116A` | `$116A` | 8 | `$1173` | `$1172` |

## ⛔ 폭 스캐너에 일괄 템플릿을 쓰지 말 것

한때 스캐너 4곳에 `AND $FC / CP $5C / JR Z,리드 / NOP NOP` 을 **일괄로** 박았다.
세 가지가 깨졌다. 전부 "빌드는 되고 부팅도 되는" 종류다.

1. **비리드 경로가 리드 경로로 떨어진다.**
   사이트마다 분기 극성이 다르다 — `JR Z,리드` 형과 `JR NZ,비리드`·`RET NZ` 형이
   섞여 있다. NOP 패딩은 전자에서만 맞다. `0x038545`·`0x0380E1` 은 후자라
   **모든 평문자가 리드 취급**을 받아 다음 바이트를 먹었다.

2. **`AND $FC` 가 A 를 파괴한다.**
   A 를 곧바로 버리는 사이트에서만 안전하다. `0x038545` 는 바로 뒤
   `CALL $489E` 의 인자가 A 이고, `0x0380E1` 은 A 를 리턴값으로 쓴다.

3. **`0x0380E1` 은 스택이 깨졌다.**
   8바이트 창이 원본 `PUSH AF`($40E8)를 덮어써서 `POP AF`($40ED)만 남았다.
   `POP AF` 가 리턴 주소를 먹고 `RET` 이 엉뚱한 데로 뛴다.

→ 지금은 사이트마다 **원본 바이트를 검증하고 전용 코드를 넣는다**
(`SCAN_SITES` 에 오프셋·CPU주소·크기·원본바이트·어셈블리를 통째로 적어 둔다).
전부 `CP $5C`/`CP $60` 범위비교라 **A 를 보존**하고, 목적지를 명시한다.

## ⛔ 오검출 — 고치면 게임이 깨지는 곳

| 오프셋 | 왜 아닌가 |
|---|---|
| `0x0380CF` | `$40B9` 의 뱅크 넘김 처리 (위 §참조) |
| `0x02E4AB` `0x02E4E9` `0x02E523` (뱅크11) | 전부 `LD A,($CFD0)` 뒤다. `$CFD0` 은 텍스트 바이트가 아니라 **장면/맵 인덱스** 전역변수 — ROM 전역에서 167회 읽고 비교 상수가 1~126 까지 넓게 퍼져 있다. 리드 검사라면 `$5E`/`$5F` 두 값뿐이어야 한다. 게다가 진짜 스캐너와 달리 **`CP $5F` 짝이 없다** |

판별 기준: **진짜 리드 스캐너는 24바이트 안에 `CP $5E` 와 `CP $5F` 가 짝으로 있다.**
ROM 전체 `CP $5E` 93건 중 짝이 있는 것은 15건이고, 그 15건이 정확히 위 사이트 목록이다.

## 검증이 통과하는 버그 (2026-08-15에 실제로 겪음)

세 개 다 "빌드 성공 + 되읽기 검증 통과 + 부팅 성공"인 채로 숨어 있었다.

### 1. 글리프 `0x5C` 에 「프」

인코더(`build_kr`)와 디코더(`verify_kr`)가 리드 목록을 **각자** 들고 있었고
둘 다 `$5E`/`$5F` 만 알았다. 인코더는 「프」를 바이트 `5C` 로 쓰고 디코더는
`5C` 를 「프」로 읽으니 **429/429 일치**가 났다. 패치된 **엔진만** `5C` 를
리드로 봐서 뒷바이트를 먹고 page3 글리프를 그렸다.

→ 규약을 `krcodec.py` 한 곳으로 모으고, `verify_kr` 이 **엔진과 같은
`iter_glyphs`** 를 쓰게 했다.

### 2. 숫자 슬롯에 한글

`0x33 0x34 0x36 0x37` 에 「로」「시」「어」「약」이 앉아 있었다.
번역문에 3·4·6·7 이 한 번도 안 나와서 "빈 슬롯"으로 잡혔기 때문이다.
그런데 **게임은 숫자를 코드로 그린다**:

```
0x038527  ADD A,$30 / CALL $489E     (한 글자 렌더)
0x03A399  ADD A,$30 / CALL $63D4     (4자리 수치)
```

HP·MP·소지금·데미지에 3/4/6/7 이 들어갈 때마다 한글이 나왔다.
`glyph_usage.py`(텍스트 참조 빈도)로는 **절대 안 보인다**.

→ `alloc_glyphs.PINNED` 로 `0x30-0x39` 와 `0x20`(공백)을 고정.
공백은 폭 스캐너가 `CP $20`(`0x0249AB`)으로 판정하므로 다른 글자가 오면
그 글자가 공백 취급된다. 교차 증거: **스페인어·프랑스어 완역 패치도
`0x20` 만은 원본과 바이트 동일**하다.

### 3. 옛 엔진 베이스로 빌드

엔진 패치를 고쳐도 `build.py` 가 손으로 만들어 둔 `out/sobs_eng02.gbc` 를
쓰고 있어 반영이 안 됐다. → `build.py` 가 **매 빌드마다 확장 ROM 에서
엔진 패치를 다시 굽는다**(0단계). 결정적이라 비용이 없다.

# 확장 2단계 — 글리프 1024 → 2048

## ✅ 1단계(1280, page4)는 **구현·실기 검증 완료** (2026-08-15, wip29)

아래 설계대로 넣었다. 실측 결과는 이 문서 맨 끝 §"1단계 결과".
여기 남은 표·주의사항은 **2단계(page5~7)** 를 넣을 때 그대로 쓴다.

## 왜 지금 필요한가

**빈 슬롯이 0 이다** (946 배정 + 78 보호 = 1024). 남은 블록을 한 글자도 못 넣는다.

| 남은 블록 | 규모 |
|---|---|
| 뱅크 134 표 5개 (필드 액션·제작·능력·성격·작전) | 230 레코드 |
| 캐릭터 리포트 (뱅크 177) | 프로필 24 + 이름 12 |
| 이벤트 대사 | ~5,175 문자열 |

번역문에 **1회만 쓰인 음절이 144개**라 문장을 다시 써서 30~60 슬롯은 짜낼 수
있지만, 이벤트 대사(수천 음절)는 그 방법으로 절대 안 된다.

## 상한이 1024인 진짜 이유

    용량 = (리드바이트 수 + 1) × 256

리드는 `$5C~$5F` 넷인데 **`$5C` 가 page3 별칭으로 낭비**돼 실질 4페이지다.
그리고 페이지 베이스가 `$4001 + p*$1000` 이라 **한 뱅크(16 KB)에 4페이지가 꽉 찬다.**
5페이지째는 베이스가 `$8001` = 뱅크 창 밖 → **두 번째 폰트 뱅크가 필수**다.

## ⛔ 그동안 못 한 이유와, 그걸 없애는 방법

기존 설계 노트: "사이트마다 뱅크를 실어 나를 안전한 레지스터가 없다"
(`0x0F87` 계열은 C 가 상위 루프 카운터, `0x039AA4` 는 `LD B,A` 로 B 를 덮는다…).
그래서 뱅크를 **상수**로 고정했고 거기서 4페이지에 갇혔다.

### 해법: 뱅크를 **베이스 주소의 최상위 비트에 실어 보낸다** (RAM 불필요)

페이지 상위바이트를 이렇게 준다.

| 페이지 | 리드 | 베이스 상위 | 폰트 뱅크 |
|---|---|---|---|
| 0 | (없음) | `$40` | `0xFA` |
| 1 | `$5E` | `$50` | `0xFA` |
| 2 | `$5F` | `$60` | `0xFA` |
| 3 | `$5D` | `$70` | `0xFA` |
| 4 | `$5C` | **`$C0`** | `0xFB` |
| 5 | `$5B` | **`$D0`** | `0xFB` |
| 6 | `$5A` | **`$E0`** | `0xFB` |
| 7 | `$59` | **`$F0`** | `0xFB` |

즉 **bit7 = 두 번째 뱅크**다. 복사 직전에 bit7 을 보고 뱅크를 고른 뒤
`RES 7,<상위>` 로 정상 주소(`$40..$70`)로 되돌린다. 운반 레지스터가 필요 없다 —
**기존 헬퍼들이 이미 세우는 그 레지스터**가 그대로 운반한다.

주소 산술은 `HL = 베이스 + A*16` 뿐이고 `$F001 + $FF0 = $FFF1` 이라 **넘침이 없다.**
베이스로 메모리를 읽는 것은 복사 루틴 안에서만 일어나므로(그 전에 bit7 을 지운다)
중간 코드가 `$C000~$FFFF` 를 건드릴 일이 없다.

### 사이트별로 **어느 레지스터의 상위바이트인지**가 다르다 (실측 확인함)

| 사이트 | 헬퍼 | 상위바이트 | 복사 루틴 | 복사원 |
|---|---|---|---|---|
| `0x000FC0` `0x00103B` `0x00111B` `0x039AD9` `0x03A3F5` | (D→H) | `H` | `$06DD` | `HL` |
| `0x0388F9` | `h_de_b` | `D` | `$2FB9` | **`DE`** (`ld a,(de)`) |
| `0x0010B4` | (D→H) | `H` | `$0DA7` | `HL` |
| `0x034438` | `h_hl_cnt` | `H` | `$06FD` | `HL` |
| `0x2C6A6F` | (B→H) | `H` | `$0D50` | `HL` (`ld a,(hl+)`) |
| `0x2C6D51` | `h_bc_de` | `B` | `$7116`(뱅크177) | 미확인 — **디스어셈블 먼저** |

⛔ `$2FB9` 는 `HL` 이 아니라 **`DE`** 에서 읽는다. 일괄 템플릿 금지의 또 다른 사례다.

### 사이트 치환 형태

원본은 전부 `LD <r>,$3D` + `CALL <복사>` = 5바이트(한 곳은 7바이트)다.
이걸 통째로 `CALL h_fb_<사이트>` + NOP 패딩으로 바꾸고, 헬퍼를 사이트마다 둔다.

```
h_fb_hl:  ld b,$FA
          bit 7,h
          jr z,.go
          res 7,h
          ld b,$FB
   .go:   jp $06DD
```

A 로 뱅크를 받는 복사 루틴(`$0DA7`/`$0D50`/`$06FD`)은 `ld a,$FA` / `ld a,$FB` 형으로.
`0x0388F9` 는 `ld c,$10` 을 헬퍼 안에 넣고 `jp $2FB9`.

### 같이 고쳐야 하는 것

1. **폭 스캐너 6곳**: 범위비교 `CP $5C` → **`CP $59`** (`CP $60` 은 그대로).
   ⛔ 사이트마다 분기 극성이 다르다 — `SCAN_SITES` 의 전용 코드를 각각 고칠 것.
2. `krcodec`: 리드 규약에 `$59~$5B` 추가. **`RESERVED_LEADS` 를 `0x59~0x5F` 로.**
   ⇒ 원본 표시문자 `$59 $5A $5B` 를 추가로 포기한다. 지금 쓰이는지 먼저 확인.
3. `alloc_glyphs`: 상한 1024 → 2048. `0x400/0x500/0x600/0x700` 도 **배정 금지**
   (인코딩하면 뒷바이트가 `0x00` 이라 문자열이 끊긴다 — 기존 `0x100/0x200/0x300` 과 같은 이유).
4. `expand_rom`: 뱅크 `0xFB` 를 만들고 **뱅크 ID 각인**.
5. 폰트 빌드: 페이지 4~7 을 뱅크 `0xFB` 의 `$4001/$5001/$6001/$7001` 에.
6. `verify_kr` · `screen_text` · `unscramble` · `glyph_usage`: 페이지 수 8.
7. **뱅크 `0x3D` 미러는 그대로 3페이지만** — 벌크 프리로드는 원본 범위(0x000~0x2FF)
   밖을 안 쓴다. 여기를 늘리려 들지 말 것.

### ⛔ 2026-08-16 정정 — `$5B`=『 를 리드로 쓰면 대사 364군데가 깨진다

이벤트 대사를 전수 추출할 수 있게 되어(`docs/10`) **실측**했다.

| 리드 후보 | 원본 글자 | 이벤트 대사에서 쓰인 횟수 | 영향받는 런 |
|---|---|---|---|
| `$59` | `Y` | **1** | 1 / 5,470 |
| `$5A` | `Z` | **12** | 6 / 5,470 |
| `$5B` | `『` | **428** | **364 / 5,470** |

`『` 는 대사에서 강조·인용에 흔히 쓰인다(캐릭터 리포트가 쓰는 것도 이미 알고 있었다).
리드로 바꾸면 **아직 번역 안 한 대사 364개가 그 자리에서 뒷바이트를 먹어** 깨진다.
번역이 다 끝나면 사라질 문제지만, 182 KB 를 다 옮기기 전까지 중간 빌드의 실기
QA 가 계속 오염된다 — 이 프로젝트에서 QA 는 번역과 같은 우선순위다(`docs/08`).

⇒ **2단계를 다시 쪼갠다.**

| 단계 | 추가 리드 | 용량 | 포기하는 원본 글자 | 실측 피해 |
|---|---|---|---|---|
| 1 ✅ | `$5C` | 1280 | 없음 | — |
| **2a** | `$5A` `$59` | **1792** | `Z` `Y` | **13회 / 7런** |
| 2b | `$5B` | 2048 | `『` | 428회 / 364런 → **대사 번역이 끝난 뒤에** |

2a 만으로 **+512 슬롯**이다(지금 빈 슬롯 178 → 690).
`Y`/`Z` 는 새 페이지에 다시 배정하면 화면상 손실이 없다.

⚠ 2a 는 리드가 **연속 범위가 아니다**($59~$5A 와 $5C~$5F, 가운데 $5B 가 빠진다).
범위비교 하나로 안 되므로 폭 스캐너 6곳과 디스패치에 `$5B` 예외를 넣어야 한다.
⛔ **일괄 템플릿 금지** 원칙은 그대로다 — 사이트마다 분기 극성이 다르다(위 §참조).

### 단계를 나눌 것 — 1단계는 **아무 글자도 포기하지 않는다**

원본에서 `$59`=`Y` `$5A`=`Z` `$5B`=`『` 는 **살아 있는 표시문자**다.
반면 **`$5C` 는 이미 리드로 잡아 놓고 page3 별칭으로 버리고 있다.**

| 단계 | 추가 리드 | 용량 | 포기하는 원본 글자 |
|---|---|---|---|
| **1** | `$5C` (page4) | **1280** | **없음** — 이미 리드다 |
| 2 | `$5B` `$5A` `$59` (page5~7) | 2048 | `『` `Z` `Y` |

1단계만으로 **+256 슬롯**이고, 뱅크 134(230 레코드) + 캐릭터 리포트(36)는
여기서 끝난다. 엔진 작업량은 1단계와 2단계가 똑같으므로(두 번째 뱅크 + bit7)
**1단계를 먼저 넣어 실기로 검증한 뒤** 2단계는 리드만 늘리면 된다.

2단계에서 `Y`/`Z` 를 포기할 때는 **새로 생긴 페이지에 `Y`/`Z` 를 다시 배정**하고
인코더가 그쪽을 쓰게 하면 화면상 손실이 없다(값으로 인덱스를 계산하는 슬롯은
`0x20` 과 `0x30-0x39` 뿐이라 글자 이동이 안전하다 — `alloc_glyphs.PINNED`).
다만 **아직 번역 안 한 원문**이 `Y`/`Z` 바이트를 쓰고 있으면 그 구간은 깨진다.
